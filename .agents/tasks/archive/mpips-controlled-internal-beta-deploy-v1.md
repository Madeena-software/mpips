# Task: Deploy MPIPS as a controlled internal beta

## Objective

For `$TARGET`, deploy the accepted MPIPS DICOM-only service locally as a
controlled internal-beta rehearsal. This task never uses SSH, contacts a
production host, or claims production readiness. An active MHCS runtime is
not required; use a task-local synthetic client for verification.

Accepted application commit:

```text
2f267aed2fd970530bb11d592f0f346feeaf2ace
```

Required endpoints:

```text
POST /v1/radiographs/dicom
GET  /health
```

The deployment must remain private and bind only to the local machine. Inspect
the local Docker state and record whether MHCS is present, but use the local
synthetic client as the only verification caller:

```text
Local model:
   task-local synthetic client -> http://127.0.0.1:${MPIPS_INTERNAL_PORT}
   MPIPS binds only to loopback.

An absent MHCS runtime is expected and is not an execution blocker. Do not
claim MHCS-context connectivity.
```

Do not assume that `localhost` inside an MHCS container reaches MPIPS.

The local rehearsal is permitted only under this release condition:

```text
The task-local synthetic client may submit only synthetic fixtures generated by
the verified burn-in script. The future beta release must accept NPZ files only
from the trusted MHCS capture path and trusted Madeena detector software.
Legacy pickle-enabled NPZ metadata remains a known residual risk contained
inside the network-disabled, non-root, resource-limited isolated worker.
Arbitrary third-party NPZ uploads are prohibited.
```

The task may prepare deployment artifacts, create one scoped local commit,
deploy the beta, run live verification, and stop.

## Scope and constraints

In scope:

- inspect local Docker state and record MHCS as `not-present` when absent;
- prepare private local deployment configuration;
- adapt only relevant Madeena deployment-template patterns;
- build immutable MPIPS API and NPZ-worker images;

- mount validated calibration artifacts read-only;
- configure the local synthetic-client connection;
- deploy locally with Docker Compose;
- run live health, route, authentication, HMAC, DICOM conversion, Redis,
  launcher, isolation, cleanup, restart, concurrency, and rollback checks;
- document the trusted-NPZ release condition;
- create one local implementation commit before deployment.

Deployment requirements:

- stack or project name: `mpips`;
- API service name: `api`;
- Swarm service name when applicable: `mpips_api`;
- no Nginx;
- no public hostname;
- no public ingress;
- loopback-only host port for the local synthetic client;
- Redis has no published port;
- Redis is accessible only to MPIPS;
- API and worker images use the deployed Git SHA, not `latest`;
- API, launcher, calibration, and workspace placement remain on the server that
  owns the required local paths and images;
- production documentation routes remain disabled;
- use one API replica for the initial beta unless shared state and local-path
  semantics are explicitly verified for more.

Trusted-NPZ beta conditions:

- only the task-local synthetic verification client may call the local service;
- only synthetic fixtures generated by the verified burn-in script may be
  submitted locally; the future beta must accept only trusted Madeena-generated
  NPZ files;
- no direct end-user or third-party upload route may be introduced;
- safe non-pickle NPZ migration remains a mandatory post-beta task;
- the limitation must be recorded in project context and deployment notes.

Local secrets and configuration:

- generate temporary local-only bearer, HMAC, Redis, and JWKS key material;
- do not read, copy, print, or commit production secret values;
- write runtime environment files with mode `0600`;
- use the local JWKS fixture and local issuer/audience created by the burn-in
  script;
- use the deterministic synthetic calibration created by the burn-in script;
- use `DEV_AUTH_BYPASS=false`;
- never carry local JWKS, synthetic secrets, or synthetic calibration into a
  production deployment.

Out of scope:

- SSH, remote deployment, production host access, or public exposure;
- TLS or public reverse proxy configuration;
- arbitrary third-party NPZ support;
- safe-NPZ migration;
- converter changes;
- DICOM semantic changes;
- calibration algorithm changes;
- generic DAG, Celery, S3, callback, webhook, or node-catalog deployment;
- production authentication provider or production calibration configuration;
- deleting legacy generic code;
- unrelated cleanup.

Do not modify:


Do not modify DICOM semantics, calibration algorithms, or the NPZ producer

Repository and server safety:

## Execution policy

- Mode: `agentic-loop`
- Maximum iterations: `6`
- Approval gates:
  - any remote host access or SSH;
  - any public exposure;
  - converter, DICOM semantic, calibration algorithm, or NPZ contract change;
  - dependency installation or upgrade;
  - destructive change to unrelated runtime resources;
  - any change outside stated scope;
  - live failure requiring product-contract changes.

```text

-> smallest scoped correction -> rerun affected verification
```

Do not weaken authentication, manifest signing, worker isolation, Redis
privacy, or verification checks.
