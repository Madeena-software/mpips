# MPIPS Release Service placement evidence and verification plan

## Purpose and boundary

This plan determines whether the owner-preferred standalone Compose project on the existing production host is acceptable. It does not perform production inspection, reserve a subnet, change infrastructure, or authorize implementation or deployment. See the [conditional placement decision](adr-mpips-b2-conditional-placement.md) and the broader [Draft Release Service architecture](adr-mpips-release-service-production.md).

No capacity thresholds are set here. The responsible infrastructure and service owners must provide workload targets and acceptance thresholds before measurements are assessed. Missing or ambiguous evidence is `unknown`, not a pass.

### Network flow allowlist to verify

The proposed client flow is Grabber **outbound HTTPS** to the owner-approved ingress; ingress reaches only the Release Service backend on its approved private path. No direct public inbound container port and no MPIPS/MHCS network attachment are proposed. Default Release Service runtime egress should be denied; any exception must be listed and approved by its owner, such as a designated backup destination or monitoring collector. DNS/time dependencies and certificate automation should terminate at the owner-approved host/ingress boundary where feasible. The network owner must enumerate actual required destinations and ports from the selected deployment design; this plan does not guess them. Verify firewall and routing rules against that allowlist and prove denied paths to protected clinical workloads remain denied.

Diagnostic envelope and public-log controls:

- Any future production run is a new work package. It requires independent review, fresh explicit owner authorization, and a pre-dispatch check for active or pending production deployment/verification workflows. Authorization for any earlier audit is not reusable.
- Run only from reviewed `main` on the approved production runner through the approved platform path. Keep the audit manual-only and isolated from existing deployment/verification concurrency; do not cancel, replace, or race those runs.
- Keep total runtime within five minutes and each fixed local inspection within three seconds, matching the existing audit collector's command timeout. Use no loops polling the host, package installation, writes, Docker mutations, network probes, load tests, service restarts, or artifact uploads.
- Run one collector at a time. Cap captured stdout/stderr at 64 KiB per fixed command; exceeding the cap produces `unknown` and stops dependent checks. Do not impose an unapproved load test or sustained sampling; representative peaks come from existing monitoring records.
- Capture outputs in process memory, parse only fixed allowlisted fields, suppress stderr/errors, and emit only the fixed categories listed above. Never print raw inventories, hostnames, domains, IPs/CIDRs, MACs, usernames, process commands/IDs, container IDs/names, paths, environment values, Docker configuration, credential locations, exact resource values, or patient/workspace data.
- Missing commands, denied access, timeouts, malformed or ambiguous output, absent owner-approved thresholds, missing candidate subnet, or uncertain source authority result in `unknown` and stop dependent inference. Stop the run if sanitization or scope cannot be demonstrated.
- Audit public setup metadata separately; the existing audit guide notes Actions platform logs may reveal runner-name metadata outside the collector. The runner owner must assess this before authorization.

This is a diagnostic proposal only. Do not implement, dispatch, or contact production as part of this plan. A diagnostic result informs the placement decision but does not itself approve a subnet, ingress, or deployment.

## Placement decision gates

| Gate | Acceptance evidence | Responsible owner | Decision still required | If unmet |
|---|---|---|---|---|
| Representative capacity | Owner-approved CPU/memory/disk/network budgets and representative peak evidence show the proposed service and download/backup demand fit without displacing existing workloads. | Infrastructure owner with MPIPS/MHCS service owners. | Define measurement period, budget and acceptable interference criteria; assess actual evidence. | Do not approve same-host placement; choose separate VM/host or obtain more evidence. |
| Storage and recovery | Artifact/retention/staging needs fit approved storage; encrypted backup and isolated restore demonstrate approved RPO/RTO. | Storage/backup and Release Service owners. | Approve retention, capacity margin, backup destination/operator and numeric recovery objectives. | Same-host placement remains unapproved; separate host still needs approved storage/recovery. |
| Isolation/network | Dedicated Compose project and network; owner-approved CIDR has no conflict; no attachment to MPIPS/MHCS networks; firewall/backend path is least-privilege and verified. | Network and security owners. | Approve network allocation and evidence sources; verify actual reachability boundary. | Do not reserve/use a range or attach service; fallback if isolation cannot be demonstrated. |
| Ingress/DNS/TLS/auth | Named approved ingress, DNS and PKI owners; private backend route; TLS renewal and authentication/access policy are operationally supported. | Ingress, DNS, PKI, identity/security owners. | Approve exact ownership, route, hostname, certificate lifecycle and client auth boundary. | No endpoint/publication; fallback if private approved route is unavailable. |
| Operational non-interference | Service owner, runbook, monitoring, maintenance window, change coordination and rollback/fallback are approved; no unacceptable impact on clinical services. | Infrastructure owner and MPIPS/MHCS service owners. | Accept shared host failure domain and change coordination. | Select separate VM/physical host if owner risk acceptance is withheld. |
| Distribution/licensing readiness | B1 trust/sequence contract has approved production interpretation; licensing review covers bundled distribution. | Release, security/key, Grabber and licensing owners. | Approve release authority, key custody/rotation, sequence scope, client identity, support policy and distribution clearance. | No implementation task or artifact publication. |

**Same-host acceptance rule:** every applicable gate must have recorded evidence and owner approval. `Unknown` is not acceptance. **Fallback rule:** if evidence is unavailable, any gate fails, or an owner rejects shared-host risk, plan the Release Service on a separate VM or physical host and repeat the ingress, network, capacity, storage, and recovery gates for that host.

## Remaining work and governance

1. Owners provide measurement budgets, operational records, identities, network/ingress/PKI source of truth, storage/backup policy, and licensing route.
2. Reviewer assesses whether owner records suffice or a separate sanitized diagnostic specification/task is needed. The diagnostic must not be executed without its separate authorization.
3. Infrastructure/security/service owners decide same-host acceptance or select the separate-host fallback and record the decision.
4. Planner updates the Draft architecture and only then may prepare a validated implementation task if the architecture and authorization gates are satisfied.

No executable Release Service task is created by this plan. The API incident remains independent, and no production access, dispatch, provisioning, infrastructure change, or deployment is authorized.
